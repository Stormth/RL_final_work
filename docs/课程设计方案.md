# 轻量大模型工具链求解算法题：课程设计方案 v1

> 代号：`algosmith`（可改）
> 定位：强化学习课程设计 · 2–3 人 · 5 周（含 1 周缓冲）
> 形态：Python 包 + CLI，本地 Qwen-Coder，LeetCode 函数式题库

---

## 0. 一句话概括

在**固定调用预算**下，学习"下一步该向哪个工具要反馈"的策略：让冻结的本地 Qwen 反复经历「写码 → 被工具打回 → 改码」，用 RL 决定工具调用顺序与止损时机，在**未见过的** LeetCode 题上以更低成本取得更高通过率。

---

## 1. 问题定义

| 项 | 定义 |
|---|---|
| 输入 | 一道 LeetCode 函数式题：题面 + `class Solution` 签名 + 2~3 个公开样例 |
| 可用资源 | 冻结的本地 LLM（Qwen-Coder 7B/14B）、Python 沙箱、**仅用于造测试**的参考解、**仅用于判定**的隐藏测试 |
| 约束 | 每题最多 `K = 8` 次"模型调用 / 工具调用" |
| 目标 | 最大化隐藏测试通过率（AC），同时最小化平均成本 |

形式化为预算约束 MDP，用拉格朗日化求解：

```
max_π  E[ 1(AC) ]        s.t.  E[ cost ] ≤ B
⟺  max_π  E[ 1(AC) − λ · cost ]      λ ∈ {0, 0.02, 0.05, 0.1, 0.2}
```

扫 λ 得到 **成本–成功率 Pareto 曲线**，这条曲线是本项目最有说服力的一张图。

---

## 2. 关键设计决策：为什么 RL 放在"编排层"

这是整个方案最需要向老师解释清楚的一点。

**做法**：LLM 只做两件事——按题面写首解、按失败信息改代码。**RL 智能体不生成代码**，它只从 7 个动作里选下一个（要公开样例？要随机对拍？要重写？要提交？）。

**三条理由**：

1. **可行性**：对 7B 模型做 policy gradient 需要成千上万条 rollout 和 ≥24GB 显存，5 周内既跑不完也调不好；编排层的状态空间小、每个 episode 只需 3–8 步，表格 Q-learning 在单机上几小时就能收敛。
2. **可解释性**：学到的策略可以直接画成"状态 × 动作"热力图，例如「出现 RE 之后倾向于 `targeted_fix`，WA 且输入规模大时倾向于 `fuzz_large`」。答辩时这是最好的素材。
3. **可对照**：同一套工具、同一个模型，只换策略（固定脚本 / 随机 / 学习），消融实验干净，能真正回答"**学习到底带来了什么**"。

**备选（加分项，非必需）**：模型层 RL —— 用 GRPO + LoRA 在"修复轨迹"上微调，奖励为测试通过。需要 ≥24GB 显存与约 1 周额外工期，放到 W6 作为 stretch goal；条件不满足就明确写进"未来工作"。

## 3. 与已有工作的差异

| 工作 | 做了什么 | 对我们的不足 |
|---|---|---|
| AlphaCodium（flow engineering） | 固定流程：题意反思 → 生成测试 → 跑公开/自造测试 → 按失败迭代 | 流程写死，不看调用成本，无策略学习 |
| LDB（ACL'24） | 按基本块切分程序，逐步验证运行时状态再让模型修 | 面向"修 bug"，不含选题与测例生成；实现重 |
| MapCoder（ACL'24） | 检索/规划/编码/调试四角色协作 | 多角色多轮开销大，本地小模型撑不住 |
| AFlow（MCTS 搜 workflow） | 在"算子图"上做蒙特卡洛树搜索 | 搜索发生在图结构层，需海量 rollout，成本极高 |
| LiveCodeBench | 防污染的代码评测基准 | 只做评测，不做工具链 |
| **本项目** | 预算内"选哪个反馈工具"的**策略学习** + 轻量可复现工具层 | — |

**差异点（写进报告的创新点）**：
1. **成本感知**：把"工具调用"当稀缺资源，优化目标带预算约束，而不是"能调多少调多少"。
2. **学习型编排 vs 固定 workflow** 的严格对照（同工具、同模型、同预算）。
3. **轻量**：不依赖 LangChain/LangGraph，`openai` + 标准库即可，CPU 也能跑工具层。
4. **数据质量工程**：LeetCodeDataset 的自动生成断言存在噪声（多解题、越界输入），我们有一套可复现的过滤流程。

## 4. 系统设计

### 4.1 架构

```
                    ┌─────────────────────────────┐
                    │  Policy π(a|s)              │  Q-table / LinUCB / BC
                    └──────────────┬──────────────┘
                                   │ action ∈ {A0..A6}
                    ┌──────────────▼──────────────┐
                    │  ToolChainEnv（gym 风格）    │
                    │  state = f(verdict, 通过率…) │
                    └───┬──────────┬──────────┬───┘
             ┌──────────▼──┐  ┌────▼─────┐  ┌─▼────────────┐
             │ LLM (Qwen)  │  │ Sandbox  │  │ Judge        │
             │ 写码 / 修复 │  │ 子进程    │  │ 逐 assert 判定│
             └─────────────┘  └──────────┘  └──────────────┘
                                   │
                          ┌────────▼─────────┐
                          │ TestFactory      │
                          │ 参考解 + 随机输入 │
                          └──────────────────┘
```

### 4.2 动作空间（7 个）

| 动作 | 做什么 | 成本 | 返回给策略的信号 |
|---|---|---|---|
| `A0 submit` | 跑全部隐藏测试 | 1 call | 仅 AC / WA（**不暴露失败用例**，逼迫策略先收集信息） |
| `A1 run_public` | 跑 2~3 个公开样例 | ~0 | 首个失败样例的输入与期望输出 |
| `A2 fuzz_small` | LLM 写随机输入生成器（n ≤ 8），跑 20 例，与参考解对拍 | 1 call | 通过率 + 首个反例（输入/期望/实际） |
| `A3 fuzz_large` | 同上，n 接近约束上界 | 1 call | 通过率 + 反例 + 实际耗时 |
| `A4 targeted_fix` | 把反例 + traceback 喂回模型，要求最小改动 | 1 call | 新代码 + 新判定 |
| `A5 rewrite` | 丢掉当前解，只给题面 + 失败摘要，换思路重写 | 1 call | 新代码 + 新判定 |
| `A6 audit` | 让模型做静态审查：复杂度 vs 约束、边界条件 | 1 call | 文本建议（不改变代码） |

`A6` 的价值在于对付"随机小样例测不出、但会 TLE"的题——这是 fuzz 的盲区。

### 4.3 状态特征

约 12 维，表格 Q 用粗离散化，LinUCB 用原始值：

- 难度 one-hot（Easy/Medium/Hard）
- 标签 multi-hot（取 top-10 高频标签）
- 已用步数 / 剩余预算
- 上次判定 one-hot（AC/WA/RE/TLE/CE/NONE）
- 最近一次 fuzz 通过率（分 4 档）
- 是否已生成过生成器（bool）
- 是否已 rewrite 过（bool）
- 当前代码长度（分档）
- 距上次改动的步数

### 4.4 奖励

```
r_t = − c_llm · 1[动作需要调模型] − c_tool · 1[执行类动作]
终局：AC → +1.0；预算耗尽 → 0；连续两次 submit 失败 → 0（提前终止）
```

λ 通过"每次模型调用记 −λ·1"注入，无需改代码即可扫参。

### 4.5 策略与算法（实验组）

1. **B0 无工具基线**：单次生成 → 直接判定（pass@1）
2. **B1 固定脚本 A**（AlphaCodium-lite）：`run_public → targeted_fix ×2 → submit`
3. **B2 固定脚本 B**：`fuzz_small → targeted_fix → fuzz_large → targeted_fix → submit`
4. **B3 随机策略**：同动作空间均匀随机（用来证明"不是随便调工具就行"）
5. **P1 表格 Q-learning（主）**：ε-greedy 衰减，状态离散化后约 2–5k 状态
6. **P2 LinUCB**：上下文 bandit，忽略长期回报，作为"短视策略"对照
7. **P3 BC + FQI（可选）**：先用混合策略采 2k 条轨迹做行为克隆预热，再离线 Q 迭代
8. **P4 DQN / PPO（附录）**：若时间允许，证明"更复杂的算法没带来更好结果"也是有价值的结论

> 训练集与测试集必须按时间切分（见 §5），否则"模型背过题"会污染结论。

### 4.6 训练循环伪代码

```python
for episode in range(N_EPISODES):
    problem = sampler.sample(train_split)
    s, done, info = env.reset(problem)
    while not done:
        a = policy.act(s, epsilon(episode))
        s2, r, done, info = env.step(a)   # 内部：LLM → 沙箱 → judge
        buffer.add(s, a, r, s2, done)
        policy.update(s, a, r, s2, done)
        s = s2
```

## 5. 数据

**数据集**：[`newfacade/LeetCodeDataset`](https://huggingface.co/datasets/newfacade/LeetCodeDataset)（Apache-2.0，数千题，含时间戳）。关键字段：

| 字段 | 用途 |
|---|---|
| `problem_description` / `starter_code` | 喂给模型 |
| `entry_point`（如 `Solution().twoSum`） | 构造 `candidate` |
| `test`（`def check(candidate)` + 一堆 assert） | 判定用；**逐 assert 执行**可得部分通过率 |
| `input_output` | 公开样例的来源 |
| `completion` | **参考解**：用于验证随机测试生成器、做对拍 oracle |
| `estimated_date` | 时间切分，防污染 |
| `difficulty` / `tags` | 状态特征与分层统计 |

**清洗流程（必须做，否则结论不可信）**：

1. **参考解自检**：`completion` 必须通过该题全部 assert，否则整题丢弃。
2. **多解题过滤**：题面含 "any order" / "any valid" / "multiple valid" 的，要么去掉，要么挂手写 checker（`judge/custom.py`，预计 10 题以内）。
3. **断言可解析性**：能按行拆出独立 assert 的才纳入（拆不出的整题跑，只给 AC/WA）。
4. **人工抽检 10%**：确认没有"参考解与断言一起错"的样本（如 two-sum 里那种违反约束的输入）。

**切分**：
- 时间切分：`estimated_date < 2024-06` → train（约 100~200 题）；`≥ 2025` → held-out test（30 题）。
- 每题的 assert 前 2~3 条 → **public**，其余 → **hidden**。
- 明确写进报告："held-out 题目的发布时间晚于模型训练截止时间"，这句话能挡掉一半答辩质疑。

## 6. 实验设计

### 6.1 指标

| 指标 | 定义 | 为什么看 |
|---|---|---|
| **AC@8** | 8 次调用内通过隐藏测试的题目比例 | 主指标 |
| pass@1 | 首解直接通过率 | 与"不用工具"对比 |
| avg_calls / avg_tokens | 平均模型调用次数 / token 数 | 成本 |
| wall_clock | 每题端到端耗时（秒） | 真实可用性 |
| **AUC(success–cost)** | 成本-成功率曲线下面积 | 单一数字概括 Pareto |

### 6.2 消融

- 去掉 `fuzz`（只留公开样例）→ 验证"随机对拍"的贡献
- 去掉 `rewrite` → 验证"止损"的价值
- 去掉 `audit` → 验证"复杂度审查"对 TLE 题的作用
- λ 扫描（0 / 0.02 / 0.05 / 0.1 / 0.2）
- 难度分层（Easy / Medium / Hard 各看一遍）

### 6.3 统计方法（小样本必须做）

- 每题用**相同首解种子**跑不同策略（common random numbers），做**配对比较**，方差能降一大截。
- 3 个随机种子 × 30 题，报告均值与 **bootstrap 95% CI**。
- 只报"均值 + 星号"是答辩被问爆的经典位置，别省这一步。

### 6.4 预期结论（先写下，防止事后编故事）

- Easy 题上工具链收益有限（模型本来就会），**Medium 是主战场**。
- 主要收益来自 `fuzz_small`：小模型最常见的失败是边界条件，不是算法思路。
- `rewrite` 在 Hard 上是止损动作，在中低难度上通常浪费预算。
- 学到的策略应当呈现"**先廉价探测、再定向修复、最后才重写**"的结构。

## 7. 五周计划与分工

三人：**A 数据/沙箱/评测**，**B 工具/模型适配/提示**，**C 环境/策略/实验管理**。

| 周 | A | B | C | 里程碑 |
|---|---|---|---|---|
| W1 | 数据加载+清洗+切分；沙箱；逐 assert judge | LLM 适配（Ollama/vLLM、缓存、重试）；三类 prompt | CLI 骨架 + 配置 + 结果目录；B0 基线脚本 | **M1**：`eval --policy naive` 跑通 20 题，出 pass@1 与耗时 |
| W2 | 公开/隐藏拆分；生成器有效性校验（参考解过滤） | fuzz / audit 工具；失败归因（CE/RE/TLE/WA）分类器 | 固定脚本 B1/B2；统计与绘图脚本 | **M2**：B1/B2 vs B0 对照表（第一张图） |
| W3 | 状态特征 + 轨迹 JSONL schema | targeted_fix / rewrite 调优；温度与格式稳定性 | ToolChainEnv；表格 Q + 随机策略；采离线日志 | **M3**：Q-learning 训练跑通，学习曲线初版 |
| W4 | 数据 bug 修复；边界 case 复现 | prompt 迭代；失败案例归类 | 3 seeds 正式实验；消融；Pareto | **M4**：主结果表 + 3 张图 |
| W5 | 单测、文档、一键复现 | 3 个题的策略差异案例分析 | 报告 + 答辩 slide + demo | **M5**：一键复现 + 报告初稿 |
| W6 | 缓冲 | 缓冲 | （可选）GRPO 加分项 | 答辩 |

**节奏约定**：每周五做一次集成，`main` 分支必须能跑通 `algosmith eval --n 5`；W2 结束**冻结功能**，之后只修 bug 和调参。

## 8. 风险与预案

| 风险 | 概率 | 影响 | 预案 |
|---|---|---|---|
| 本地 7B 首解通过率过低（<15%） | 高 | 高 | **Day 1–3 先做 spike 测**；不行就退到 Easy 子集、换 14B，或允许首解采样 2 次 |
| 随机测试生成器大量无效 | 高 | 中 | 必须"参考解跑通"才算有效；无效则回退到只用公开样例；报告里给出 fuzz 覆盖率 |
| 每题 LLM 太慢（>40s） | 中 | 高 | vLLM 并发 8；prompt 缓存；压缩上下文；题目数降到 20 |
| RL 学不出效果（样本少、方差大） | 中 | 高 | 动作空间砍到 4 个；BC 预热；配对同种子；实在不行把"为什么没学出来"写成负结果分析——这依然是合格的课程设计 |
| 题库泄漏（模型见过原题） | 高 | 中 | 时间切分 + 扰动测试（改数值/改题面表述）；报告里明确声明 |
| 范围蔓延（想加 Web UI） | 中 | 高 | W2 末冻结；UI 只做终端里彩色打印每一步 |

## 9. 验收标准

1. `pip install -e . && algosmith eval --config configs/main.yaml` 一条命令复现全部主结果，产出 `summary.md` + 4 张图。
2. 30 题 held-out 上：在 `avg_calls ≤ B1` 的预算内，P1 的 AC 率不低于 B1（或给出显著性分析说明为何不能）。
3. `judge` / `sandbox` / 清洗逻辑有单测；GitHub Actions 绿。
4. 报告含：相关工作对比、MDP 形式化、策略设计、实验与消融、失败分析、复现说明。
